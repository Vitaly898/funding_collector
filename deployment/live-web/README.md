# Web-live: подготовка к контролируемой проверке на VPS

Это отдельный браузерный путь к существующему signer/worker, не legacy `controller`
и не прежний paper UI. **Развёртывание приложения не подтверждает работоспособность
реального аккаунта или принятие биржей ордера.** Сначала приватные чтения, затем
отдельно согласованная минимальная сделка. Не используйте основной кошелёк.

## Границы

- Linux x86_64, Docker Engine и Docker Compose, отдельное приложение и data volume.
- Один владелец, одна пара и один рабочий процесс. Нет многопользовательской модели.
- Seed phrase и основной owner private key приложению не нужны. Вводятся только
  отдельные execution/agent credentials, созданные и зарегистрированные вручную на
  соответствующих площадках. Протокольные права могут быть шире локальных лимитов.
- Ключи зашифрованы существующим KeyStore, пароль шифрования не сохраняется.
  Потеря пароля делает сохранённые credentials недоступными. Это не защита от root
  или скомпрометированного VPS/браузера/SDK; immutable Python copies нельзя надёжно
  стереть. Секреты передаются серверу через HTTPS, это не client-side signing.
- Авторизация web-сессии и ARM ограничены по времени; рестарт начинает с заблокированной
  торговлей. Перезапуск, logout или блокировка **не отменяют ордера и не закрывают
  позиции**. UNKNOWN/ATTENTION требуют сверки на биржах, а не нового root/intent.
- Primary post-only LIMIT, затем ровно один защищённый IOC по полностью подтверждённому
  base quantity. IOC может исполниться частично; приложение не досылает скрытый hedge.
- Для завершённого набора нужны обе ноги и достаточная маржа на обеих площадках.
  Минимальный объём/шаг/маржа определяются контрактами и аккаунтами, а не примерным бюджетом.
- EVEDEX/Variational в новом private worker отсутствуют. Списки Hyperliquid native,
  Entropy io, Lighter Core/RH, Aster и Extended загружаются автоматически только для
  выбранной биржи, без ticker allowlist. Непроверенные/неактивные контракты отключены.
  Проверки namespace, collateral, ID, единиц, шагов/минимумов и свежести сохранены.
  Соответствие экономического риска двух контрактов выбирает оператор; равные base
  количества не доказывают delta-neutrality. Aster USDT не приравнивается к USD/USDC.
  Автоциклы/закрытие — только native HL и Lighter Core/RH; остальные — однократный набор.
- TLS на вашем домене, реальный VPS, account permissions и real order acceptance
  проверяются отдельно. Не называйте локальные fixture-тесты доказательством этих свойств.

## 1. До запуска

Нужен отдельный DNS hostname (далее `trade.example.com`) с A-записью на VPS.
Если AAAA-запись есть, она тоже должна вести на этот VPS. Порты TCP 80/443 должны
быть свободны и доступны Caddy для ACME HTTPS; Python backend 8765 **не открывается**
наружу. Если на VPS уже есть reverse proxy/другие сайты, не заменяйте их конфигурацию
и не освобождайте занятые порты без отдельного плана интеграции.

Дайте приложению примерно 1 GiB RAM и 1 CPU, Caddy ещё 128 MiB; оставьте запас хосту
и другим сервисам. Это лимиты контейнеров, не обещание стабильной работы при любом
наборе SDK/рынков. Не выдавайте контейнеру Docker socket, root SSH, Hermes `.env`,
его volumes или папки других проектов. Не выключайте Hermes ради теста автоматически.

Используйте **проверенную и отдельно опубликованную** ветку `qa-agent/live-web-vps`.
До публикации её нельзя клонировать с GitHub. Проверяйте полный commit SHA из итогового
отчёта, а не только имя ветки. Не разворачивайте старую `master`, ожидая web-live.

## 2. Сборка и первый локальный владелец

Из корня опубликованного checkout. Единственная переменная ниже — публичный DNS,
это не пароль или ключ. Не сохраняйте секреты в `.env`, compose, shell history или Git.

```sh
export FC_DOMAIN=trade.example.com
docker compose -f deployment/live-web/compose.yaml config
docker compose -f deployment/live-web/compose.yaml build app
# Интерактивный masked prompt, до открытия веб-сервера; минимум пароля проверяется CLI.
docker compose -f deployment/live-web/compose.yaml run --rm --no-deps -it app init --root /data
# После успешного init. Старт не создаёт торговой authority.
docker compose -f deployment/live-web/compose.yaml up -d app caddy
docker compose -f deployment/live-web/compose.yaml ps
```

`init` не создаёт аккаунтов биржи, не регистрирует ключи и не пополняет баланс.
Повторный init не должен перезаписывать существующего владельца. Если служба уже
развёрнута, не используйте init как сброс пароля/истории. Нужен отдельный план восстановления.

Данные приложения находятся в именованном `app_data` volume, TLS Caddy — в отдельных
`caddy_data`/`caddy_config`. Пользователь приложения UID/GID 10001, private data 0700,
секретные файлы 0600. При переходе на bind mount оператор должен заранее выставить
корректного владельца/права, а не запускать приложение root или chmod 777.

Compose специально использует общую network namespace приложения и Caddy:
Caddy обращается к `127.0.0.1:8765`, передаёт исходный Host, а наружу публикуются только
80/443. Подменённый `X-Forwarded-*` не должен менять origin/auth policy приложения.

## 3. Проверка браузером

1. Откройте **https://trade.example.com**. Убедитесь, что сертификат действителен.
   Не вводите пароль/ключи при HTTP, ошибке сертификата или через чужой TLS-прокси.
2. Войдите паролем владельца, созданным через masked init. До входа приватные API
   не должны отдавать состояние, аккаунты, ключи или доступ к настройке.
3. Настройте две реальные identity и лимиты. Откройте создание стратегии и выберите
   инструменты из автоматически загружаемых отдельных списков; поиск/кнопка загрузки
   не нужны. Расчёт цены и сохранение не запускают торговлю. ID берутся из metadata,
   не вводятся вручную. Aster private symbol — точный baseAsset, wire mapping `*USDT`
   выполняется адаптером; его локальный SHA-256 scope ID не является биржевым index.
   Старые Aster ordinal IDs 0/1/2 отклоняются: конфигурацию нужно создать заново.
   Extended synthetic IDs и vault передаются как точные десятичные строки без JS округления;
   `fee_rate_cap` задаётся явно как доля, например `0.0005`.
4. Для каждой ноги введите только dedicated execution key и отдельную passphrase
   шифрования (16+ символов для существующего KeyStore). Extended требует своего
   typed credential bundle, не owner-wallet key. Поля должны очищаться после отправки.
5. Сначала выполните **проверку аккаунтов без торговли**. Должны быть подтверждены
   registration/account binding, показаны фактические позиции и число открытых ордеров.
   Публичный стакан, локальная schema validation и старый journal этого не заменяют.
6. Перед торговлей проверьте реальные лимиты/маржу, отсутствие посторонних ордеров и
   возможность вручную отменить/закрыть позицию через интерфейсы обеих бирж.
7. Только после отдельного решения введите fresh passphrases обеих ног, точно
   `ARM EXACT SCOPED ORDERS` и явно запустите набор. Сам login или check не разрешают
   отправку ордера. Не запускайте несколько вкладок/копий приложения для обхода отказа.
8. Сверьте real fills, base quantity, позиции, комиссии по каждой валюте и остаток с
   интерфейсами бирж. ACK/NEW не являются fills; durable observation может устареть.

На первой проверке не тестируйте намеренный обрыв связи/kill на реальных деньгах.
Crash/UNKNOWN сначала воспроизводятся только fixture-тестами. Не вводите новый intent
после неоднозначного исполнения, пытаясь заставить сервис повторить ордер.

## 4. Остановка, обновление, резервная копия

Кнопка блокировки, logout, expiry и завершение процесса отзывают локальное право новых
отправок, **но не снимают выставленные ордера**. Сначала вручную убедитесь в состоянии
обеих бирж. Не считайте `down` безопасным способом закрыть экспозицию.

```sh
# Не удаляет volumes. Не добавляйте -v.
docker compose -f deployment/live-web/compose.yaml down
```

Резервная копия private volume должна храниться зашифрованной, отдельно от кода и
пароля шифрования. Не отправляйте её в Telegram/issue/PR. Не удаляйте signer/worker
ledger: это write-ahead duplicate barrier и история reconciliation, не cache.
Обновлять код/контейнеры только после проверки отсутствия незавершённого исполнения;
при пересоздании app пересоздайте и Caddy с общей network namespace:

```sh
# Только после отдельного согласованного обновления и остановленного исполнения.
docker compose -f deployment/live-web/compose.yaml up -d --force-recreate app caddy
```

## Локальные проверки и их область

`tests_fc/test_live_web_deployment.py` проверяет build-context allowlist, no-secret
manifest, hardening и реальный Compose config render, если Compose CLI доступен.
Это **не** запуск Docker image, проверка сертификата или успешная сделка. Standalone
Compose для теста можно передать через `FC_TEST_COMPOSE`; это тестовая настройка,
не переключатель безопасности runtime. В текущем окружении Docker daemon недоступен,
поэтому image build/container smoke должны быть отдельно подтверждены перед VPS acceptance.
Runtime lock объединяет совместимые зависимости native и Extended и должен проходить
`pip check`; нельзя бездумно накладывать старый `requirements-extended.lock` поверх
native lock (конфликт верхних границ eth-account/eth-utils).
